# v0.3.0 — 2026-10-27

Three kinds of failure survive the 0.2.x pipeline with every gate green.
This release adds five phase rows, one scope question and a close-time verdict for them, and repairs two defects in how a wave closes.
The plugin is also renamed to `wave-orchestrator`.

## What's new

### `[BEN]` the benefit contract, at Phase 0.8

A wave whose success criterion is "build the component and touch nothing else" runs every control on the component and none on the outcome.
RED and GREEN are written from the same brief, so a wrong brief still produces a green suite, and the output-alignment check compares the build with the spec rather than the outcome with reality.
`[BEN]` makes you write down, before any criteria exist, one sentence saying what a person or the surrounding system does differently once the feature works — a sentence that may not name anything the wave introduces — plus a census of everything already in the code that decides that same outcome, and a count of the files outside the feature's own directory the wave expects to change.

It runs when you answer yes to "does this wave change existing behaviour?".

### `[BEN-CLOSE]` the benefit verdict, at Phase 12.5

Stating the benefit is worth little if nothing checks it at the end.
After the last hardening phase and before the version bump, a separate team re-runs the test that backs the benefit, searches for anything the wave introduced that no other part of the system reads, and collects any note the wave itself left saying the existing system overrides the new behaviour.
It then writes `BENEFIT: DELIVERED` or `BENEFIT: UNDELIVERED` with reasons; either way the wave commits and closes, because a hard block here would only invite weakening the sentence to get out of it.

### `[UIA]` user-intent criteria, at Phase 0.5

"The `status` enum gains `ON_HOLD`" is testable and says nothing about what anyone sees.
Waves that add a new kind of record, or a new value of an existing one, need criteria in the user's voice before the technical ones: *as a role, when I do this against that data state, I expect this outcome*.
Every user-intent criterion has to be covered by at least one acceptance criterion, and the output-alignment check maps both to evidence.

It runs when you answer yes to "does this wave introduce a new kind of record, or a new value of an existing classification, that a user will see?".

### `[ES]` empty-state scan, at Phase 4.2

On the day of a deploy there are no records of the new kind, and anything whose presence depends on a non-zero count is absent for every real user — while every fixture-seeded test passes.
`[ES]` reads the acceptance criteria's data-state matrix and, for each user-visible surface, simulates the state with no records at all and the state with only the records that existed before the wave, reporting anything that renders only when a count is non-zero.
`[BF-ES]` at Phase 4.3 fixes what it finds, with your approval per fix, like every other bug-fix row.

It runs on the same answer as `[UIA]`.

### A data-state matrix on acceptance criteria

Not a phase, a writing rule.
Every criterion that asserts on something a user sees now names what it claims in three states: no records at all, only the records that existed before this wave, and records in every new value.
The brutal review at Phase 1.2 rejects a criterion that only says what happens when the new data exists.

## What changed for existing users

- **Two questions before the wave starts.** `/wave-start` asks whether the wave introduces new vocabulary and whether it changes existing behaviour before it creates the wave, then asks about UI and the code-review gate as before. In full mode the first two must be answered before anything can be dispatched, because acceptance criteria now come after the two new phases. An unanswered question is never read as "no".
- **Design Review runs on more waves than the documents used to say.** `[DR]` engages when the wave ships UI **or** changes existing behaviour. The engine has enforced that since 0.2.0; sixteen places in the documentation still said "UI waves only", and they now say what actually happens.
- **The pipeline is 31 rows.** 18 run in every full-mode wave. 7 are the fix rows that run only when the scan before them reported findings. 6 depend on your scope answers or on whether the benefit contract ran. Demo mode is unchanged — the same five phases, the same gates. Solo mode is unchanged.
- **A wave closes when its work is finished.** Full mode closes once version bump, commit, cleanup and checkpoint are all done; demo closes on the end-to-end phase, as before. Every ordered row must be done, or skipped by mode or by a scope answer of "no". A question still unanswered, a scan that is done but left no readable findings count, or a row that failed or is waiting for a redo keeps the wave open. The dashboard never counts, and its stop never closes a wave.
- **Only the stop that finishes the work closes the wave, and it says so once.** After the close is confirmed it prints, in this order: the leftover warning if background work, scheduled jobs or watchers remain (it names the scorecard), the delivery warning if the verdict calls for one, and the scorecard pointer unless the leftover warning already gave it. Each appears at most once per wave. If the close itself fails, you get one state warning naming `scripts/wave-close.sh`, nothing is marked, and the next closing stop tries again.
- **The end of a turn never closes a wave.** In full and demo mode, when a turn ends on a wave that is complete but still open, you get one state warning saying so and naming `scripts/wave-close.sh` — no verdict and no pointer — every time, until the wave is closed. In 0.2.1 the end of a turn could print the leftover warning or the scorecard pointer; in full and demo mode both now come only from the closing stop. Solo mode keeps its pointer at the end of a turn.
- **A new warning, `W-UNDELIVERED`,** appears once at the close when the delivery verdict is `undelivered`, or `unverified` because nothing checked, always together with the scorecard pointer. In solo and demo mode the verdict is `not-applicable`, because the benefit contract does not run there. `scripts/wave-scorecard.sh` prints the verdict under a `## Delivery` heading.
- **`scripts/wave-close.sh` decides under the wave lock.** It reads the state again once it holds the lock and closes only the open wave it first saw. Run by hand, it refuses with exit status 1 when the wave changed or was closed while it waited; re-run it to close the current wave.
- **The plugin is renamed from `claude-wave-plugin` to `wave-orchestrator`,** because the host's plugin validator reserves the old prefix. The marketplace entry is renamed too, so remove the old marketplace entry and add it again, then install `wave-orchestrator`. The repository URL is unchanged for now.

## Fixed

- **The first dashboard stop closed a full-mode wave.** Since 0.2.0 a wave was closed when the last row of its mode was marked done, and in full mode that row is the dashboard — which may run at any time and produces no artifact. So the first dashboard dispatch that finished closed the wave, whatever else had or had not run, and every hook went quiet for the rest of the work. Wave completion now means every ordered row is done or skipped, and the dashboard does not count.
- **The scorecard pointer never appeared.** It was printed when a wave was active and its last phase was done, but the call that marked that phase done also closed the wave in the same breath, so in full and demo mode the two conditions were never true together. The pointer is now emitted by the handler that closes the wave, once per wave, after it has confirmed the close.
- **The two commit-message guards disagreed.** The in-session commit guard and the `commit-msg` hook installed by `wave-init.sh` each kept their own list of refused attribution lines, and between them a session line and a co-author line at the vendor's mail domain could get through one or the other. Both now read one pattern, `WV_TRAILER_ERE` in `scripts/hooks/lib.sh`, and refuse the same five forms; a plain mention of the tool or plugin name in a message is still accepted.

## For contributors

- **Several warnings from one call.** A test case can now assert the exact ordered list of rule ids a hook call emits: `expect.rules` on the stdout channel and `expect.stderr_rules` on stderr, where the closing stop writes its close-time warnings. A case declares exactly one of `rule`, `rules` and `stderr_rules`. See `tests/cases/README.md`.
- **The test run cleans up after itself.** A green run removes its scratch directory; a failed run, or one with `WV_KEEP_TMP=1`, keeps it and prints its path. A case registers its own cleanup with `wv_on_exit` instead of installing an exit trap, and the mutation drivers keep their scratch inside their own temporary root.
- **Generic prose.** Documentation, comments and messages no longer name a vendor, a model or a specific host product; the model-tier routing words, the host's protocol keys and environment names are unchanged.

## Upgrading

The state schema is unchanged and there is no migration. A wave already in flight when you upgrade behaves like this:

| Wave in flight | What happens |
|---|---|
| `AC` not done, behaviour-change unanswered | `AC` is denied until you answer it. 0.2.x always wrote this flag as unanswered, so this is the common case. Run `scripts/wave-set.sh behaviour-change true\|false` |
| `AC` not done, behaviour-change `true` | `[BEN]` is required before `[AC]`, and `[BEN-CLOSE]` before the tail |
| `AC` already done | `[BEN]` cannot run and `[BEN-CLOSE]` is skipped; the rest of the wave is unchanged. If behaviour-change is `true`, the wave closes `unverified` and says so once |
| Any 0.2.x wave | The vocabulary flag is absent, so `[UIA]` and `[ES]` are skipped |
| Dashboard not yet dispatched | The wave no longer closes when it is |
| Wave already closed by a dashboard stop | It stays closed |
| Wave complete but still open (its closing stop was blocked or failed) | The end of each turn says so; close it with `scripts/wave-close.sh` |

To move an existing install to the new name, remove the old marketplace entry, add it again and install `wave-orchestrator`; uninstall `claude-wave-plugin`.

New waves get the four questions from `/wave-start`. A wave you drive by hand has to answer vocabulary and behaviour-change before its first full-mode dispatch.

If you have anything that reads "the dashboard phase closes the wave" out of the 0.2.x specification, it needs to use wave completion instead.

## What is next

0.3.1 is planned to add the two checks that have to happen after a deploy rather than before it: a walk of the live application against each criterion's route, and a first-time-user walk by someone holding only the tester guide. Alongside them, an end-to-end run against a baseline that contains no records of the new vocabulary, which is what every installation looks like on the day it receives the change. All three need a `deploys` scope flag and cannot be verified locally the way this release can.
